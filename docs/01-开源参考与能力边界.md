# 开源参考与能力边界

本文档说明 `aiflow-kit` 应该借鉴哪些现有工具，以及第一版明确不做哪些能力。

## 可借鉴对象

| 参考 | 可借鉴点 | 本项目采用方式 |
| --- | --- | --- |
| Agent Skills 标准 | `SKILL.md`、`scripts/`、`references/`、`assets/` 的轻量目录模型，以及 progressive disclosure | 作为 Skills 源格式，保证 Claude Code 与 Codex 都容易适配 |
| `anthropics/skills` | 真实 Skills 的组织方式、元数据、复杂资源拆分方式 | 学习写法，不直接复制业务无关内容 |
| Claude Code Plugins | `.claude-plugin/plugin.json`、插件根目录 `skills/`、命名空间、marketplace 分发 | 生成 Claude Code 插件包 |
| Codex Skills | `.agents/skills` repo 级发现、用户级 `$HOME/.agents/skills`、`agents/openai.yaml` 可选元数据 | 生成 Codex 本地 Skills 和插件包 |
| Codex Plugins | `.codex-plugin/plugin.json`、`.agents/plugins/marketplace.json`、插件内 `skills/` | 生成 Codex 插件包和本地 marketplace |
| Superpowers | brainstorming、plan、TDD、review 等软件工程流程技能化 | 借鉴流程颗粒度和强制验证思路，不绑定其实现 |

## 本项目的核心差异

`aiflow-kit` 不是另一个大而全的 agent 框架。它只解决 AI 编程流程容易漂移的问题：

- 项目上下文如何稳定提供。
- 开发前如何强制计划。
- 实现过程如何跟已有测试和代码风格对齐。
- 前端改动如何形成截图或浏览器验证闭环。
- 提交前如何做结构化 review。

## 组件边界

| 组件 | 做什么 | 不做什么 |
| --- | --- | --- |
| Skills | 给 AI 读的流程说明、触发条件、输出格式 | 不做复杂扫描、不保存状态、不调用不确定外部服务 |
| CLI | 扫描项目、读取 Git diff、生成 Markdown 报告、运行配置命令 | 不接 LLM、不自动改业务代码、不自动提交 |
| 模板 | 生成 `AGENTS.md`、`CLAUDE.md`、`.aiflow/config.toml` | 不覆盖用户已有规则，默认先备份或跳过 |
| 插件包 | 把 Skills 分发给 Claude Code 或 Codex | 不内置高权限 MCP，不默认连接第三方账号 |
| MCP 集成 | 第二阶段按需声明外部能力 | 第一版不自带 MCP server |

## 全局与项目级边界

为了避免污染所有项目，第一版默认只把通用能力做成全局：

- 可以全局：`aiflow` CLI、通用 Skills、通用 review/TDD/frontend 验证流程。
- 必须项目级：`AGENTS.md`、`CLAUDE.md`、`.aiflow/config.toml`、`.aiflow/context.md`、项目命令、风险路径、业务规则、项目定制 Skills。
- 谨慎全局：MCP、hooks、带权限的自动化能力。

全局安装必须是显式动作，不能由 `aiflow init` 或默认 `aiflow install-skills` 顺手写入用户目录。详细规则见 [07-全局与项目级边界.md](07-全局与项目级边界.md)。

## 第一版不做清单

- 不做 Web UI。
- 不做自己的代码图谱系统，后续可接 Graphify 或其他代码索引工具。
- 不做自动任务调度平台。
- 不做跨团队权限系统。
- 不做 secret 管理。
- 不做 CI 平台替代品。
- 不做一键自动发布。

## 可复用但不要强依赖的开源能力

| 能力 | 建议 |
| --- | --- |
| Playwright | 前端验证阶段可调用项目已有 Playwright，第一版只发现和提示命令 |
| Graphify | 如果项目存在图谱报告，`project-analysis` 优先读取；没有则回退到文件扫描 |
| GitHub CLI | `code-review-release` 可提示 `gh pr create`，但第一版不自动执行 |
| Figma MCP | 有设计稿时作为外部集成，不写入 MVP 阻塞项 |
| Superpowers skills | 可作为流程参考，不把外部 skill 当运行时依赖 |

## 设计取舍

Skills 和 CLI 必须分工清晰。Skills 负责告诉 AI “该怎么做”，CLI 负责给 AI “确定性材料”。这样做的原因：

- Skills 在 Claude Code 和 Codex 之间更容易移植。
- CLI 输出 Markdown，任何 agent 都能读。
- 不依赖特定平台的 tool 名称，减少迁移成本。
- 团队可以先只使用文档和模板，再逐步启用 CLI 和插件。
