# 配置界面技术路线

本文档比较 `aiflow-kit` 配置界面是一步到位做 Tauri 桌面端，还是先做 React Web 端，再按需要封装桌面端。

## 背景

当前 `aiflow-kit` 已有三类交互面：

- CLI：负责确定性命令、配置读写、验证、打包和项目扫描。
- 浏览器伴随插件：负责 Chrome / Edge 中的页面上下文采集、DevTools 元素读取和受控自动化任务执行。
- 文档与 Skills：负责流程规范、设计约束和 Agent 协作方式。

浏览器插件的定位应保持轻量。它需要接触浏览器权限、DevTools API 和页面上下文，不适合继续承载复杂设置、项目管理、Agent 状态、数据库 profile、远程连接等管理 UI。配置界面应从插件中抽离，成为独立控制台。

## 决策结论

推荐路线：

```text
React Web 控制台 MVP
  -> 固化本地 API、状态模型和 UI 组件
  -> 按需要封装为 Tauri 桌面端
```

不建议当前一步到位 Tauri。Tauri 可以作为后续分发形态，但第一阶段更适合先用 React Web 做配置控制台。

## 方案 A：一步到位 Tauri 桌面端

### 优点

- 用户体验更完整：像一个独立应用，不依赖用户自己打开浏览器页面。
- 更适合长期承载本机能力：托盘、文件选择、系统通知、启动本地服务、检查路径等能力更自然。
- 分发边界清楚：未来可以打包为 Windows 桌面程序，降低非技术用户使用门槛。
- 安全边界可更细：Tauri 命令可以明确声明本机能力，而不是把所有能力暴露给 Web 页面。

### 代价

- 初始工程复杂度高：需要 Rust/Tauri 工程、桌面打包、权限、签名、升级策略和跨平台验证。
- 与当前 Python CLI 的关系需要设计清楚：桌面端是调用 `aiflow` 子进程，还是嵌入服务，还是通过本地 HTTP API。
- 开发验证链路更重：普通配置页面修改也要考虑桌面窗口、系统 WebView、Tauri command、构建产物。
- 过早绑定分发形态：如果配置模型还会变化，桌面壳会放大迁移成本。

### 适合时机

Tauri 更适合在这些条件成熟后引入：

- 配置 UI 的核心信息架构已经稳定。
- 已经有本地 API 或 IPC 协议，而不是让 UI 直接拼 CLI 命令。
- 需要托盘、系统通知、文件选择、开机启动、后台守护进程等桌面特性。
- 面向非开发者分发，用户不应手动启动 Web 服务。

## 方案 B：先做 React Web 控制台

### 优点

- 速度快：可以先聚焦配置项、状态展示、表单校验、任务队列、验证结果等产品问题。
- 与桌面端兼容：React 前端可以后续被 Tauri 直接加载，核心 UI 不需要推倒重写。
- 验证简单：复用现有前端设计、Playwright 验证和本地 dev server 流程。
- 边界清楚：浏览器插件继续保持零依赖轻量运行时，配置控制台独立演进。
- 更适合 Agent 开发：Codex / Claude 可以用普通 Web 工作流实现、截图验证、查 DOM、跑测试。

### 代价

- 第一阶段仍需要用户启动本地服务或 CLI 命令打开页面。
- 如果 Web 页面直接访问本地 HTTP API，需要处理 token、CORS、loopback 访问控制和危险操作确认。
- 某些桌面能力只能先做成占位或通过 CLI 间接完成。

### 适合当前阶段的原因

当前 `aiflow-kit` 的核心风险不是“有没有桌面壳”，而是：

- 配置项越来越多，CLI-only 不够直观。
- 浏览器插件不应继续变大。
- 需要把项目配置、local secrets、Agent 状态、验证命令、浏览器 bridge、数据库 profile 等信息组织成可扫描界面。
- 需要先确定 UI 的信息架构和后端接口边界。

这些问题用 React Web 可以更快迭代。等界面成熟后，Tauri 只负责提供桌面分发、本机能力和启动体验。

## 推荐架构

第一阶段先新增一个独立 Web 控制台，而不是改浏览器插件：

```text
apps/config-web/             # React + Vite 控制台
  src/
  package.json

src/aiflow/commands/ui.py    # aiflow ui serve / open
src/aiflow/core/ui_api.py    # 本地 API handler 或服务逻辑

.aiflow/
  config.toml                # 非敏感项目配置
  *.local.toml               # 本机 secret 和私有路径
```

推荐交互链路：

```text
React Web UI
    |
    | localhost API + project token
    v
aiflow ui serve
    |
    +-- 读取/写入 .aiflow/config.toml
    +-- 读取脱敏后的 local 配置状态
    +-- 调用 verify / doctor / browser doctor
    +-- 展示 agent 状态和最近报告
```

后续 Tauri 形态：

```text
Tauri Shell
    |
    +-- 加载同一套 React build
    +-- 启动或连接 aiflow 本地服务
    +-- 提供文件选择、通知、托盘、启动器等桌面能力
```

## UI 范围

React Web MVP 不做大而全，先做配置工作台：

- 项目概览：项目名、根目录、aiflow 状态、最近验证结果。
- 配置编辑：`project`、`commands`、`frontend`、`browser`、`review`、`skills`。
- 本机私有配置状态：只显示是否存在、变量名、路径脱敏状态，不展示 secret。
- Browser companion：bridge 是否启用、端口、token 文件状态、extension dir、打包入口。
- Agent 状态：`.aiflow/agents/status.md` 摘要、运行中任务、handoff 文件链接。
- 验证中心：运行 `doctor`、`verify --auto`、查看 `.aiflow/verify.md`。

不在 MVP 做：

- 不直接编辑浏览器插件页面。
- 不执行任意 shell 命令。
- 不把 secret 明文传给前端。
- 不做用户全局配置写入。
- 不做复杂多窗口桌面体验。

## API 与安全边界

本地 UI 服务必须遵守项目级边界：

- 默认只监听 `127.0.0.1` 或 `localhost`。
- 需要项目 token，token 保存在 `.aiflow/ui/token` 或沿用已有安全模型。
- 写配置只允许白名单字段，不接收任意文件路径写入。
- local secrets 只允许写入 `.aiflow/*.local.toml`，前端读取时脱敏。
- 所有高影响操作必须明确按钮触发，例如运行验证、生成 token、打包浏览器插件。
- 不允许 Web UI 直接运行任意命令；命令只能映射到已有 `aiflow` 子命令或受控 API。

## 技术选择

推荐第一阶段：

| 层 | 技术 | 原因 |
| --- | --- | --- |
| UI | React + Vite + TypeScript | 生态稳定，后续可被 Tauri 复用 |
| 样式 | CSS Modules 或轻量组件库 | 控制体积，避免一开始引入过重运行时 |
| 状态 | React Query 或轻量 fetch wrapper | 本地 API 状态、刷新、错误处理足够 |
| 后端 | Python `aiflow ui serve` | 复用现有 CLI、配置解析、路径边界和测试体系 |
| 验证 | Playwright + `aiflow verify` | 符合现有前端验证文档 |

Tauri 阶段再引入：

| 层 | 技术 | 原因 |
| --- | --- | --- |
| 桌面壳 | Tauri | 轻量桌面分发和本机能力 |
| IPC | Tauri commands + localhost API 二选一 | 根据当时安全边界决定 |
| 本机能力 | 文件选择、通知、托盘、启动服务 | 只承载 Web 做不好的能力 |

## 目录建议

建议不要放在 `extensions/browser/`，而是放在独立应用目录：

```text
apps/
  config-web/
    src/
    index.html
    package.json
    vite.config.ts
```

理由：

- 避免浏览器插件包体变大。
- 避免扩展权限和配置控制台权限混在一起。
- 方便后续 Tauri 直接引用 `apps/config-web` 的 build。
- 方便 Playwright 单独验证配置台。

## 迁移到 Tauri 的触发条件

满足任意两个条件后，再启动 Tauri：

- 配置控制台已经覆盖 80% 常用配置流程。
- 用户需要双击启动，而不是手动运行 `aiflow ui serve`。
- 需要系统托盘、通知、文件选择、自动启动后台服务。
- 需要面向非开发者分发。
- Web UI 的本地 API 和权限模型已经稳定。

## 实施路线

### Phase 1：React Web 原型

- 新增 `apps/config-web`。
- 新增 `aiflow ui serve`，只提供只读 API：项目状态、配置读取、报告读取。
- 做项目概览、配置只读查看、验证结果查看。
- 用 Playwright 验证桌面和移动视口。

### Phase 2：受控配置写入

- 增加白名单配置写入 API。
- 支持 `commands`、`frontend`、`browser`、`review` 配置编辑。
- 增加表单校验和变更预览。
- 对 local secret 只做存在性和脱敏展示。

### Phase 3：操作中心

- 支持运行 `doctor`、`verify --auto`、`browser doctor`。
- 支持浏览器插件打包入口。
- 支持 Agent 状态查看和任务 handoff 摘要。

### Phase 4：Tauri 封装

- 用 Tauri 加载同一套 React build。
- 桌面端负责启动本地服务、选择项目目录、通知和托盘。
- 保持 Web UI 与桌面 UI 的业务组件一致。

## 验收标准

React Web MVP：

- 不改浏览器插件运行时。
- 可以读取当前项目 `.aiflow/config.toml` 并展示主要配置。
- 可以展示 verify / doctor 报告摘要。
- 不泄露 `.local.toml` secret。
- 桌面和移动视口无明显布局溢出。

Tauri 首版：

- 可以打开最近项目或选择项目目录。
- 可以启动或连接 `aiflow ui serve`。
- 可以加载同一套 React 控制台。
- 不要求替代 CLI，只提供更好的本机入口。

## 最终建议

当前先做 React Web，不一步到位 Tauri。

关键不是放弃桌面端，而是把桌面端变成后续包装层：React Web 负责产品形态、配置模型和交互闭环；Tauri 负责成熟后的本机启动、分发和桌面能力。这样浏览器插件保持轻，配置台可快速迭代，未来迁移桌面端也不会被迫重写核心 UI。
