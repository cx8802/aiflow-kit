# 全局与项目级边界

`aiflow-kit` 必须明确区分“全局能力”和“项目能力”。默认策略是：通用流程可以全局安装，项目上下文必须项目内保存。这样可以避免某个项目的命令、目录、风险规则、业务约束污染所有项目。

## 总原则

```text
全局只放通用能力
项目内放具体事实
团队级放稳定标准
临时信息只放 .aiflow 生成物
```

判断标准：

- 如果内容适用于所有代码仓库，可以全局。
- 如果内容依赖某个项目的技术栈、命令、目录、业务规则，必须项目级。
- 如果内容只适用于某个团队或组织，放团队插件或团队模板，不放个人全局。
- 如果内容由扫描生成，放 `.aiflow/`，不要写入全局规则。

## 可以做成全局的内容

| 类型 | 建议位置 | 原因 |
| --- | --- | --- |
| 通用 Skills | Claude/Codex 用户级插件或用户级 skills 目录 | 分析、计划、TDD、review 这些流程跨项目通用 |
| `aiflow` CLI | 系统 PATH、`pipx`、用户环境 | CLI 是工具，不携带项目事实 |
| 通用代码审查原则 | 全局 Skill 或团队 Skill | 例如先看 diff、按严重程度列 findings |
| 通用前端验证原则 | 全局 Skill | 例如桌面/移动截图、检查溢出、空状态、交互状态 |
| 通用安全边界 | 全局规则的极短摘要 | 例如不自动提交、不泄露 secret、不执行未知命令 |
| 团队稳定流程 | 团队插件 marketplace | 适合多个项目共享，仍应避免写具体项目路径 |

全局内容应该抽象、短、稳定。它应该回答“遇到这类任务怎么做”，而不是回答“这个项目是什么”。

## 必须放项目级的内容

| 类型 | 建议位置 | 原因 |
| --- | --- | --- |
| 项目技术栈 | `.aiflow/context.md`、`AGENTS.md`、`CLAUDE.md` 摘要 | 每个项目不同 |
| 安装、测试、构建、启动命令 | `.aiflow/config.toml` | 误用到其他项目会造成错误执行 |
| 高风险路径 | `.aiflow/config.toml` | 例如 `payment/`、`auth/`、`migrations/` 只对当前项目有意义 |
| 项目业务规则 | `AGENTS.md` / `CLAUDE.md` | 例如权限模型、数据口径、禁止修改目录 |
| 项目定制 Skills | `.agents/skills/` 或项目插件 | 例如某系统的发布流程、数据库约束、内部 API 规范 |
| 代码图谱报告 | 项目目录，例如 `.graphify/` 或 `.aiflow/context.md` | 图谱只对应当前代码库 |
| 验证记录和 review 输入 | `.aiflow/verify.md`、`.aiflow/review.md` | 是一次改动的上下文，不应复用到其他项目 |

项目级内容应该能随仓库一起审查、版本控制或被 `.gitignore` 明确管理。

## 不应该全局化的内容

这些内容全局化风险很高：

- 某项目的 `npm test`、`pnpm build`、`pytest` 参数。
- 某项目的数据库、支付、权限、发布流程。
- 某项目的内网域名、token、账号、环境变量。
- 某项目的目录结构和模块解释。
- 某项目的一次性 bug 分析、review 结论、截图路径。
- 某个团队尚未稳定的实验性 Skill。

## 推荐安装矩阵

| 能力 | 个人全局 | 团队全局 | 项目级 | 默认 |
| --- | --- | --- | --- | --- |
| `aiflow` CLI | 可以 | 可以 | 不需要 | 全局安装 CLI |
| 通用 aiflow Skills | 可以 | 可以 | 可以 | 项目内试用，稳定后全局 |
| `AGENTS.md` / `CLAUDE.md` | 只放极短个人偏好 | 团队可提供模板 | 必须 | 项目级 |
| `.aiflow/config.toml` | 不可以 | 不可以 | 必须 | 项目级 |
| `.aiflow/context.md` | 不可以 | 不可以 | 必须 | 项目级生成 |
| 项目定制 Skill | 不建议 | 仅团队同类项目 | 推荐 | 项目级 |
| MCP 配置 | 谨慎 | 谨慎 | 按项目需要 | 项目级优先 |
| hooks | 谨慎 | 谨慎 | 按项目需要 | 默认不启用 |

## 安装器默认策略

`aiflow install-skills` 的默认行为应该保守：

```bat
aiflow install-skills
```

等价于：

```bat
aiflow install-skills --target codex-repo
```

也就是只安装到当前项目，不污染用户全局目录。

全局安装必须显式声明：

```bat
aiflow install-skills --target codex-user --confirm-global --allow-global
aiflow install-skills --target claude-user --confirm-global --allow-global
```

如果命令检测到目标是用户目录，应提示：

```text
You are installing skills globally. Only generic workflow skills should be installed here.
Project-specific commands, paths, business rules, and generated context must stay in the project.
```

## 模板写入规则

`aiflow init` 只写当前项目：

- `AGENTS.md`
- `CLAUDE.md`
- `.aiflow/config.toml`
- `.aiflow/context.md`

它不应该修改：

- `$HOME/.agents/AGENTS.md`
- `$HOME/.agents/skills`
- `$HOME/.codex/config.toml`
- `$HOME/.claude/CLAUDE.md`
- Claude/Codex 的全局插件目录

除非用户显式使用 `--global` 或对应安装命令。

## Skill 编写边界

通用 Skill 可以写：

```text
运行项目配置中的测试命令，并记录未运行原因。
```

通用 Skill 不应该写：

```text
运行 pnpm test:unit && pnpm test:e2e。
```

项目规则可以写：

```text
本项目验证顺序：pnpm lint -> pnpm test:unit -> pnpm build。
```

这条规则只应在当前仓库的 `AGENTS.md`、`CLAUDE.md` 或 `.aiflow/config.toml` 中出现。

## 污染检查清单

每次准备全局安装前，检查内容里是否包含：

- 具体项目名、产品名、客户名。
- 具体目录路径。
- 具体命令参数。
- 内网域名、secret、token、账号。
- 一次性调试结论。
- 只对一个仓库成立的技术栈判断。

命中任意一项，就不要全局安装。

## 推荐落地方式

第一阶段：

- CLI 全局安装。
- Skills 安装到项目 `.agents/skills/` 或生成本地插件包。
- 所有配置保存在 `.aiflow/config.toml`。

第二阶段：

- 经过多个项目验证后，把通用 aiflow Skills 打成个人或团队全局插件。
- 项目定制内容仍保留在项目内。

第三阶段：

- 团队只发布稳定、通用、无项目事实的 marketplace。
- 每个项目继续通过 `aiflow init` 管理自己的规则和验证命令。
