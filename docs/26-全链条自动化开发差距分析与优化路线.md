# 全链条自动化开发差距分析与优化路线

本文回答一个具体问题：`aiflow-kit` 已经有 `context`、`plan`、`verify`、`review`、`agents`、`browser`、`claude-agent` 等能力，为什么真实使用时仍然感觉“全链条自动化开发没有打通”？

结论是：当前系统已经有工具，但还没有任务运行时。

现在的 `aiflow-kit` 更像一个项目级 AI 编程工具箱。它能生成上下文、写计划、跑验证、做评审、管理多 Agent 目录、采集浏览器上下文、调用 Forge API。但这些能力之间缺少统一的任务 ID、状态机、结构化产物和交付闸门。用户和 Agent 仍然要靠聊天上下文把链路串起来，所以一旦任务变长、会话中断、验证失败或多 Agent 参与，链路就会断。

下一阶段不应该继续横向堆命令，而应该先补一根主线：`workflow run`。

## 一页结论

### 当前问题

| 环节 | 已有能力 | 主要缺口 | 体感问题 |
| --- | --- | --- | --- |
| 需求输入 | 用户直接描述任务 | 没有任务 ID 和任务规格 | 后续步骤靠聊天记忆维持 |
| 上下文 | `aiflow context --compact` | 上下文没有变成执行约束 | Agent 看了资料，但不一定按边界执行 |
| 计划 | `aiflow plan`、`.aiflow/plan.md` | 单文件承载所有任务 | 多次任务容易覆盖，无法恢复 |
| 实现 | Codex / Claude Code / Agent 手动执行 | CLI 不知道实现阶段和变更范围 | 状态只存在于对话里 |
| 验证 | `aiflow verify --auto` | 只有 Markdown 结果，没有结构化门禁 | 失败后不能驱动下一步 |
| 评审 | `aiflow review` | 只看 diff，缺少和任务规格的比对 | review 结果难闭环 |
| 多 Agent | `.aiflow/agents/` | 未绑定到某次任务 run | 多 Agent 像并行写建议，不像协同执行 |
| 交付 | `review.md`、手写总结 | 没有 finish 状态和交付摘要 | 完成标准不稳定 |
| 记忆 | `aiflow memory` | 没有从任务中提炼候选事实 | 项目知识沉淀依赖人工 |

### 推荐改造

先做一个最小任务运行时：

```text
.aiflow/runs/<run-id>/
  state.json
  input.md
  spec.md
  context.md
  plan.md
  changes.json
  verify.md
  verify.json
  review.md
  review.json
  summary.md
  events.jsonl
```

新增或调整命令：

```bat
aiflow workflow start "实现 xxx"
aiflow workflow status
aiflow workflow resume <run-id>
aiflow workflow verify <run-id>
aiflow workflow review <run-id>
aiflow workflow finish <run-id>
```

做到这一步，`aiflow-kit` 才从“命令集合”进入“任务闭环”。

同时，项目上下文应拆成两层图谱：

```text
CodeGraph：代码结构层
Graphify：项目知识层
```

对应命令：

```bat
aiflow codegraph scan
aiflow graphify build
```

`CodeGraph` 负责模块、符号、入口点等代码事实；`Graphify` 负责文档、记忆、概念和知识关系。workflow run 可以引用这两层，但不应该把它们混成一个“大上下文”。

## 目标状态

全链条自动化开发不是让 Agent 无限制地自动改代码，也不是把所有确认都取消。它应该做到：

- 任务有唯一 ID。
- 任务有明确规格、边界和验收标准。
- 每个阶段有状态和产物。
- 验证和评审能阻止交付。
- 中断后能恢复。
- 多 Agent 有明确输入、输出和责任范围。
- 高风险动作必须显式授权。
- 完成后能生成交付摘要和记忆候选。

理想链路如下：

```text
需求输入
  -> 创建 workflow run
  -> 读取 CodeGraph 代码结构
  -> 读取 Graphify 项目知识
  -> 刷新项目上下文
  -> 生成任务规格 spec
  -> 生成执行计划 plan
  -> Agent / 多 Agent 执行
  -> 收集变更 changes
  -> 运行验证 verify
  -> 运行评审 review
  -> finish 门禁检查
  -> 生成 summary
  -> 生成 memory 候选
```

这条链路里，智能部分负责理解、计划、实现和解释；确定性部分负责状态、文件、命令、验证、审计和边界。

## 当前架构诊断

当前实现可以分成五层：

```text
用户 / Agent
  |
  v
项目规则与 Skills
  - AGENTS.md
  - CLAUDE.md
  - .agents/skills/
  |
  v
aiflow CLI
  - init / context / compact / memory
  - plan / workflow / verify / review
  - agents / claude-agent / browser
  - db / nacos / ssh / wsl / forge
  |
  v
core 确定性能力
  - config / project_scan / memory
  - browser bridge
  - database profiles
  - remote helpers
  - forge APIs
  |
  v
.aiflow 项目状态
  - config.toml
  - context.md / context.compact.md
  - plan.md / verify.md / review.md
  - memory.md
  - agents/
  - *.local.toml
```

这个分层基本正确。问题不是模块方向错了，而是缺少把这些模块组织起来的运行时层。

当前的 `.aiflow/` 更像“项目资料目录”，还不是“任务状态目录”。`context.md`、`plan.md`、`verify.md`、`review.md` 都是有用产物，但它们没有共同挂在一个 run 下，也没有结构化关系。

## 实际使用链路为什么断

### 1. `workflow` 是命令聚合，不是任务编排

当前 `aiflow workflow` 可以把 `context -> plan -> verify -> review` 串起来，这比手动敲命令好。但它仍然只是一次性命令序列。

它缺少：

- run id。
- active run。
- run 状态。
- run 目录。
- 阶段产物。
- 失败恢复。
- finish 门禁。

因此一旦验证失败，系统只知道某个命令失败了，不知道这个失败属于哪个任务、阻塞哪个阶段、下一步该修复还是重新规划。

### 2. 上下文没有升级为任务规格

`aiflow context --compact` 解决的是“让 Agent 快速理解项目”。但自动化开发还需要回答：

- 本次任务允许改哪些文件？
- 哪些目录是高风险？
- 哪些验证必须跑？
- 哪些行为不属于本次任务？
- 有哪些问题需要先问用户？

这些不应该只靠 Agent 自觉遵守，而应该写进 `spec.md`。否则上下文只是资料，不是约束。

这里需要区分两类输入：

- `CodeGraph`：从代码中扫描出来的结构事实，例如模块、类、函数、入口点。
- `Graphify`：从文档和 memory 中沉淀出的项目知识，例如设计原则、约束、概念关系。

任务规格应该同时引用两者：先用 `CodeGraph` 判断影响范围，再用 `Graphify` 判断设计约束。

### 3. 计划没有和变更、验证、评审绑定

`.aiflow/plan.md` 当前是一个全局计划文件。它适合记录当前工作，但不适合承载多次任务历史。

真实使用中会出现：

- 任务 A 的计划还没收尾，任务 B 又覆盖了计划。
- Agent 根据聊天继续做，但文件里看不出当前任务。
- review 无法判断 diff 是否偏离 plan。
- final summary 只能人工拼。

计划应该进入 run 目录，并和 `changes.json`、`verify.json`、`review.json` 一起构成本次任务证据链。

### 4. 验证结果没有成为门禁

`verify.md` 对人可读，但不够让程序判断。

如果没有 `verify.json`，后续命令只能靠解析 Markdown 或完全不检查。这样 `finish`、`release`、`memory suggest` 都没法可靠判断任务是否真的通过。

验证应该输出两份结果：

- `verify.md` 给人看。
- `verify.json` 给命令和 Agent 判断。

最小结构：

```json
{
  "ok": true,
  "generated_at": "2026-05-23T23:10:16+08:00",
  "commands": [
    {
      "name": "test",
      "command": "python -m unittest discover -s packages/aiflow-cli/tests",
      "exit_code": 0,
      "required": true
    }
  ]
}
```

### 5. 评审还没有形成 issue 闭环

`review.md` 适合读，但不适合跟踪问题。

下一阶段应增加 `review.json`：

```json
{
  "ok": false,
  "findings": [
    {
      "id": "R001",
      "severity": "high",
      "blocking": true,
      "file": "packages/aiflow-cli/src/aiflow/commands/verify.py",
      "line": 42,
      "title": "Configured verification commands run through shell",
      "status": "open"
    }
  ]
}
```

这样 `finish` 可以明确拒绝阻塞问题未关闭的任务。

### 6. 多 Agent 缺少任务边界

现有 `.aiflow/agents/` 能表达协作，但没有和具体 run 绑定。

更好的方式是：

```text
.aiflow/runs/<run-id>/agents/
  architect/
    input.md
    output.md
    status.json
  implementer/
    input.md
    output.md
    status.json
  reviewer/
    input.md
    output.md
    status.json
```

每个 Agent 至少要有：

- 输入。
- 产出。
- 允许修改范围。
- 禁止事项。
- 完成状态。
- 验收方式。

否则多 Agent 只是多个会话并行，不是可控协作。

### 7. 浏览器、数据库、SSH、Forge 需要进入 run policy

这些能力很关键，但默认自动纳入主链路会有风险。

数据库能力已经先进入最小 workflow：`workflow start` 会把数据库能力和已配置 profile 摘要写入 run 的 `state.json` 与 `spec.md`，并提供 `aiflow workflow db ...` 作为 `db add/list/show/test/tables/query` 的工作流入口。后续还应该把浏览器、SSH、Forge 也纳入同一类 run policy。

它们应该逐步变成 run policy 下的受控能力：

```json
{
  "allowed_tools": {
    "browser_capture": true,
    "db_read": true,
    "db_write": false,
    "ssh_run": false,
    "forge_release": false
  }
}
```

这样 Agent 能知道哪些能力可用，CLI 也能拒绝越界动作。

## 最小可行闭环

第一版不要做复杂调度器，也不要急着做 GUI。最小可行闭环只需要解决四件事：

1. 有 run。
2. 有 spec。
3. 有结构化 verify/review。
4. 有 finish 门禁。

### 新增目录

```text
.aiflow/
  runs/
    20260523-231000-optimize-workflow/
      state.json
      input.md
      spec.md
      context.md
      plan.md
      changes.json
      verify.md
      verify.json
      review.md
      review.json
      summary.md
      events.jsonl
    current -> 20260523-231000-optimize-workflow
```

Windows 下如果不想处理符号链接，可以用文本文件：

```text
.aiflow/runs/current
```

内容是当前 run id。

### `state.json`

```json
{
  "id": "20260523-231000-optimize-workflow",
  "goal": "优化 src 工作流",
  "status": "planned",
  "created_at": "2026-05-23T23:10:00+08:00",
  "updated_at": "2026-05-23T23:12:00+08:00",
  "stages": {
    "context": "done",
    "spec": "done",
    "plan": "done",
    "implementation": "pending",
    "verify": "pending",
    "review": "pending",
    "finish": "blocked"
  }
}
```

### `spec.md`

```markdown
# Task Spec

## Goal

优化 src 工作流，让全链条自动化开发能形成闭环。

## Non-goals

- 不自动提交。
- 不自动 push。
- 不改用户全局配置。

## Allowed Changes

- packages/aiflow-cli/src/aiflow/commands/workflow.py
- packages/aiflow-cli/src/aiflow/core/workflow.py
- tests/test_workflow.py
- docs/

## Required Verification

- python -m unittest discover -s packages/aiflow-cli/tests
- python -m compileall packages/aiflow-cli/src

## Risks

- workflow 改动会影响所有使用者的标准入口。
- run 目录设计会影响后续兼容性。
```

### `events.jsonl`

```jsonl
{"time":"2026-05-23T23:10:00+08:00","type":"run.created","message":"Created workflow run"}
{"time":"2026-05-23T23:11:00+08:00","type":"context.generated","path":".aiflow/runs/20260523-231000-optimize-workflow/context.md"}
{"time":"2026-05-23T23:18:00+08:00","type":"verify.completed","ok":true}
```

事件日志不是为了复杂分析，而是为了让 Agent 和用户知道刚才发生了什么。

## 命令设计

### `aiflow workflow start`

职责：

- 创建 run id。
- 写入 `input.md`。
- 刷新 context。
- 生成 spec 草案。
- 生成 plan 草案。
- 设置 current run。

示例：

```bat
aiflow workflow start "实现用户登录失败次数限制"
```

输出：

```text
created: .aiflow/runs/20260523-231000-login-rate-limit
status: planned
next: implement according to spec.md and plan.md
```

### `aiflow workflow status`

职责：

- 显示 current run。
- 显示阶段状态。
- 显示最近事件。
- 显示阻塞原因。

示例输出：

```text
Run: 20260523-231000-login-rate-limit
Goal: 实现用户登录失败次数限制
Status: implemented

Stages:
- context: done
- spec: done
- plan: done
- implementation: done
- verify: failed
- review: pending
- finish: blocked

Blocking:
- verify failed: python -m unittest discover -s packages/aiflow-cli/tests
```

### `aiflow workflow verify`

职责：

- 对 current run 或指定 run 执行验证。
- 写 `verify.md` 和 `verify.json`。
- 更新 state。

```bat
aiflow workflow verify
aiflow workflow verify 20260523-231000-login-rate-limit
```

### `aiflow workflow review`

职责：

- 基于 git diff、spec、plan、verify 结果生成评审。
- 写 `review.md` 和 `review.json`。
- 标记阻塞问题。

### `aiflow workflow finish`

职责：

- 检查 required verification 是否通过。
- 检查 blocking review findings 是否关闭。
- 生成 `summary.md`。
- 生成 memory 候选。
- 将状态改为 delivered。

不做：

- 不自动 commit。
- 不自动 push。
- 不自动 release。

## 架构调整建议

### 1. 新增 `core/workflow.py`

放确定性状态逻辑：

- `create_run(root, goal)`
- `current_run(root)`
- `load_run(root, run_id)`
- `update_state(run, stage, status)`
- `append_event(run, event)`
- `write_run_file(run, name, content)`

命令层只处理 argparse 和打印。

### 2. 新增 `commands/workflow.py` 子命令结构

当前 `workflow` 是一个单函数入口，下一阶段应改成子命令：

```text
aiflow workflow start
aiflow workflow status
aiflow workflow resume
aiflow workflow verify
aiflow workflow review
aiflow workflow finish
```

保留兼容：

```bat
aiflow workflow "目标" --check
```

可以映射为：

```text
start -> verify -> review
```

### 3. `verify` 支持结构化输出

现有 `run_verify(args)` 可以继续生成 `.aiflow/verify.md`。新增可选参数或内部函数，让 workflow 能指定输出目录：

```python
run_verification(root, output_dir, auto=True, continue_on_error=False) -> VerificationResult
```

CLI 命令再把 result 渲染成 Markdown。

### 4. `review` 支持读取 spec 和 verify

评审不应该只看 git diff。workflow review 应额外读取：

- `spec.md`
- `plan.md`
- `verify.json`
- `changes.json`

这样评审能回答：

- 变更是否超出范围。
- 必要验证是否缺失。
- 是否有高风险路径。
- 是否满足任务目标。

### 5. 顶层文件保持兼容

为了不破坏现有使用方式：

- `.aiflow/context.md` 继续生成。
- `.aiflow/context.compact.md` 继续生成。
- `.aiflow/plan.md` 继续可用。
- `.aiflow/verify.md` 继续可用。
- `.aiflow/review.md` 继续可用。

但 workflow run 内要保存副本。长期看，顶层文件是“当前视图”，run 目录才是“事实来源”。

## 使用体验对比

### 现在

```bat
aiflow context --compact
aiflow plan "实现 xxx"
# Agent 手动编码
aiflow verify --auto --continue-on-error
aiflow review
# 人工总结
```

问题是每一步之间没有强关系。

### 优化后

```bat
aiflow workflow start "实现 xxx"
# Agent 根据 .aiflow/runs/current/spec.md 和 plan.md 编码
aiflow workflow verify
aiflow workflow review
aiflow workflow finish
```

优势：

- 每次任务有独立目录。
- 中断后能恢复。
- 验证失败会阻止 finish。
- review 阻塞问题会阻止 finish。
- 交付摘要自动生成。
- 后续可接 memory suggest、forge release、多 Agent。

## 分阶段路线

### Phase 1：Run Model

目标：建立任务容器。

交付：

- `.aiflow/runs/<run-id>/`
- `.aiflow/runs/current`
- `state.json`
- `events.jsonl`
- `workflow start/status/resume`

验收：

- 同一仓库可以创建多个 run。
- current run 可查询。
- 中断后可以恢复 run。
- 不再依赖单个 `.aiflow/plan.md` 表达全部任务状态。

### Phase 2：Spec And Plan

目标：把上下文变成执行契约。

交付：

- `spec.md` 模板。
- `plan.md` run 副本。
- 从 context、memory、用户输入生成 spec 草案。
- allowed changes / required verification / risks 字段。

验收：

- 每次实现前都有任务规格。
- Agent 可以只读 run 目录恢复任务。
- review 能检查 diff 是否超出 spec。

### Phase 3：Verification Gate

目标：让验证成为门禁。

交付：

- `verify.json`
- `workflow verify`
- `finish` 检查验证状态。

验收：

- required verification 失败时不能 finish。
- 验证结果可被程序读取。
- 用户能看到失败命令和失败原因。

### Phase 4：Review Gate

目标：让评审问题可以跟踪。

交付：

- `review.json`
- blocking findings。
- finding status。
- `workflow review`

验收：

- blocking finding 未关闭时不能 finish。
- review 能引用 spec、plan、verify。
- 评审不再只是散文报告。

### Phase 5：Agents And Delivery

目标：接入多 Agent 和交付沉淀。

交付：

- run 内 agents 目录。
- worker 输入/输出/状态。
- `summary.md`
- `memory suggest --from-run`
- forge release 前检查 delivered 状态。

验收：

- 多 Agent 产出能汇总到同一个 run。
- 交付摘要能说明目标、变更、验证、评审和剩余风险。
- 项目记忆只从确认后的 summary 中产生候选。

## 源码配套优化

为了支持上面的路线，源码层面建议同步做这些收敛：

| 优化点 | 原因 | 建议 |
| --- | --- | --- |
| CLI 注册模块化 | `cli.py` 已经越来越像总线 | 每个命令模块提供 `configure_parser(sub)` |
| TOML 写入统一 | config/db/nacos/ssh/env 都在手写 serializer | 抽 `core/toml_writer.py` |
| 测试拆分 | `test_cli_smoke.py` 过大 | 拆成 workflow、browser、db、forge、agent 等测试文件 |
| CodeGraph / Graphify 分层 | 代码结构和项目知识混在上下文里 | `codegraph scan` 写 `.aiflow/codegraph/`，`graphify build` 写 `.aiflow/graphify/` |
| 包资源修复 | 浏览器插件包资源依赖源码目录 | 将 `extensions/browser` 纳入包资源或复制到 assets |
| 高风险能力显式化 | db/ssh/forge 不应被隐式自动调用 | 纳入 run policy |
| verify/review 纯函数化 | workflow 需要复用结果，不只是打印 | core 返回结构化 result，commands 负责渲染 |

这些优化不是为了代码洁癖，而是为了让自动化链路有可靠状态源。

## 不建议现在做的事

- 不建议先做大型 GUI。没有 run model，GUI 只是把离散命令包装得更漂亮。
- 不建议让 Claude Agent SDK 默认写代码。先让它做只读分析、review、context compact 更稳。
- 不建议默认自动 commit / push / release。先把 finish 状态做好。
- 不建议让浏览器插件承载配置中心。插件应该轻量，配置和任务状态应回到 CLI / GUI。
- 不建议继续只加新命令。没有主线，命令越多，使用越碎。

## 判断是否真正打通

满足下面条件，才算初步打通全链条自动化开发：

- 用户输入目标后能创建 run。
- Agent 能从 run 恢复任务，不依赖聊天历史。
- spec、plan、changes、verify、review、summary 都挂在同一个 run id 下。
- 验证失败会阻止 finish。
- blocking review finding 会阻止 finish。
- 多 Agent 产出能进入同一个 run。
- 高风险工具受 run policy 控制。
- 完成后能生成清晰 summary。
- 可复用经验能作为 memory 候选，而不是直接污染 memory。

最终目标不是“AI 自动把所有事做完”，而是“每次工程任务都能被稳定推进、验证、评审、恢复和沉淀”。这是 `aiflow-kit` 从工具箱变成工作流运行时的关键一步。
