# 双端适配架构

`aiflow-kit` 同时支持 Claude Code 和 Codex，但不能把两端的规则文件、插件清单和 Skills 发现机制混在一起。项目内保持一份源 Skills，再由安装器生成或复制到不同目标。

## 总体分层

```text
aiflow-kit source
  |
  |  skills/                 # 一份源 Skills
  |  templates/              # AGENTS.md / CLAUDE.md / config.toml
  |  src/aiflow/             # CLI
  v
目标项目
  |
  |-- AGENTS.md              # Codex 项目规则入口
  |-- CLAUDE.md              # Claude Code 项目规则入口
  |-- .aiflow/config.toml    # aiflow 配置
  |-- .aiflow/context.md     # CLI 生成的项目上下文
  |-- .agents/skills/        # Codex repo 级 Skills，可选
  |-- .claude/settings.json  # Claude Code 项目设置，可选
```

## 适配目标

| 目标 | 规则入口 | Skill 入口 | 插件入口 |
| --- | --- | --- | --- |
| Claude Code | `CLAUDE.md` | 插件根目录 `skills/<name>/SKILL.md` | `.claude-plugin/plugin.json` |
| Codex | `AGENTS.md` | `.agents/skills/<name>/SKILL.md`、`$HOME/.agents/skills` | `.codex-plugin/plugin.json` |
| 通用 Agent | Markdown 报告 | Agent Skills 标准目录 | 不保证支持 |

## 源目录设计

仓库内建议保留一份中立源格式：

```text
aiflow-kit/
├── skills/
│   ├── project-analysis/SKILL.md
│   ├── implementation-plan/SKILL.md
│   ├── tdd-development/SKILL.md
│   ├── frontend-verify/SKILL.md
│   └── code-review-release/SKILL.md
├── plugin-targets/
│   ├── claude-code/
│   │   └── .claude-plugin/plugin.json
│   └── codex/
│       └── .codex-plugin/plugin.json
├── templates/
│   ├── AGENTS.md
│   ├── CLAUDE.md
│   ├── config.toml
│   ├── plan.md
│   ├── review.md
│   └── verify.md
└── src/aiflow/
```

`skills/` 是唯一需要长期维护的流程源。两个插件目标只做包装和少量平台元数据。

## 工作流调用关系

```text
用户请求
  |
  v
Claude Code / Codex 读取项目规则
  |
  v
根据触发条件选择 Skill
  |
  v
Skill 要求 agent 调用 aiflow CLI
  |
  v
CLI 生成 .aiflow/*.md
  |
  v
agent 根据报告实施、验证、review
```

## AGENTS.md 与 CLAUDE.md 的职责

两者都应该短，不写长篇流程细节，只写：

- 项目固定约束：包管理器、测试命令、禁止修改区域。
- aiflow 使用约定：改动前先读 `.aiflow/context.md` 或运行 `aiflow context`。
- 验证要求：提交前运行 `aiflow verify` 或列出未运行原因。
- 文档指针：复杂流程看 Skills，不把所有细节塞进规则文件。

## 目录优先级建议

对于目标项目，推荐采用这套优先级：

1. 项目级规则：`AGENTS.md`、`CLAUDE.md`。
2. 项目级配置：`.aiflow/config.toml`。
3. 项目级 Skills：`.agents/skills`，只放与该项目强相关的定制 Skill。
4. 用户级插件：Claude Code 或 Codex 的个人插件目录。
5. 团队 marketplace：当流程稳定后再分发。

## 全局与项目级边界

默认采用“项目优先、全局保守”的策略。通用流程可以全局安装，项目事实必须留在项目目录。详细规则见 [07-全局与项目级边界.md](07-全局与项目级边界.md)。

| 内容 | 放全局 | 放项目级 | 说明 |
| --- | --- | --- | --- |
| `aiflow` CLI | 可以 | 不需要 | 工具本身不携带项目事实 |
| 通用 Skills | 可以 | 可以 | 例如分析、计划、TDD、review |
| `AGENTS.md` / `CLAUDE.md` | 只放极短个人偏好 | 必须 | 项目命令和业务约束不要写全局 |
| `.aiflow/config.toml` | 不可以 | 必须 | 测试、构建、风险路径都是项目特定 |
| `.aiflow/context.md` | 不可以 | 必须 | 扫描结果只对应当前仓库 |
| 项目定制 Skills | 不建议 | 推荐 | 例如某项目 API、数据库、发布流程 |
| MCP / hooks | 谨慎 | 按项目需要 | 权限和副作用应局部化 |

防污染原则：

- `aiflow init` 只写当前项目，不改用户全局规则。
- `aiflow install-skills` 默认安装到当前项目。
- 安装到用户级目录必须显式传入全局参数。
- 任何包含项目名、目录路径、命令、业务规则、secret 的内容都不能全局化。

## 跨端兼容要求

源 `SKILL.md` 必须避免直接写死某个 agent 的专有工具名。需要工具时按能力描述：

- 用“读取文件/搜索代码/运行命令”，不要写死某个工具 API。
- 前端验证写“打开浏览器并截图”，平台适配层再决定用 Browser、Playwright 或人工命令。
- MCP 能力写成可选增强，不作为默认前提。
- 输出必须是 Markdown，便于两端消费。

## 失败回退

如果插件不可用，用户仍应能使用：

```bat
aiflow init
aiflow context
aiflow plan
aiflow review
aiflow verify
```

这意味着 CLI 是最低可用层，插件和 Skills 是体验增强层。
